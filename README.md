# Telegram-боты: короткая и долгая память

Примеры Telegram-ботов на **aiogram 3.x** с нейросетью через **ProxyAPI**.

| Скрипт | Тип памяти | Хранение |
|--------|-----------|----------|
| `bot_short_memory.py` | Короткая (history buffer) | Оперативная память (`dict`) |
| `bot_long_memory.py` | Долгая (RAG + документы) | ChromaDB (папка `./memory`) |
| `bot_combined_memory.py` | Обе сразу (гибрид) | `dict` + ChromaDB |

## Бот с короткой памятью

- Для каждого пользователя (`user_id`) хранится последние **10 сообщений** диалога.
- При новом сообщении бот отправляет модели всю историю + текущее сообщение.
- Ответ модели добавляется в историю и отправляется пользователю.

## Требования

- Python 3.11+
- Токен Telegram-бота
- API-ключ ProxyAPI

## Установка

```bash
# Создать виртуальное окружение

# Активировать

source .venv/bin/activate

pip install -r requirements.txt
```

## Настройка

Задайте переменные окружения:

| Переменная          | Описание                    |
|---------------------|-----------------------------|
| `TG_BOT_API_KEY`    | Токен Telegram-бота         |
| `PROXYAPI_API_KEY`  | API-ключ ProxyAPI           |

Самый простой способ — создать файл `.env` в корне проекта:

```
TG_BOT_API_KEY=ваш_токен_бота
PROXYAPI_API_KEY=ваш_ключ_proxyapi
```

Бот автоматически загрузит его при запуске (через python-dotenv).

Пример (Windows PowerShell):

```powershell
$env:TG_BOT_API_KEY = "ваш_токен_бота"
$env:PROXYAPI_API_KEY = "ваш_ключ_proxyapi"
```

Пример (Linux/Mac):

```bash
export TG_BOT_API_KEY="ваш_токен_бота"
export PROXYAPI_API_KEY="ваш_ключ_proxyapi"
```

## Бот с долгой памятью (RAG)

1. Пользователь загружает файл (**PDF**, **TXT** или **DOCX**).
2. Бот извлекает текст (`load_document`), разбивает его на чанки по ~500 символов
   с перекрытием 50 символов.
3. Чанки превращаются в эмбеддинги (`embed_chunks`) и сохраняются в **ChromaDB**
   (persistent storage в папке `./memory`).
4. На вопрос пользователя бот ищет релевантные фрагменты (`retrieve_context`)
   и передаёт их модели вместе с вопросом.
5. Модель отвечает строго по найденному контексту (`answer_question`).

Команды: `/start` — инструкция, `/clear` — очистить базу документов.

## Гибридный бот

Объединяет оба подхода:
- Короткая память: последние 10 сообщений диалога в оперативке.
- Долгая память: документы → эмбеддинги → ChromaDB с изоляцией по `user_id`.
- Перед ответом модель получает **и** историю диалога, **и** релевантные фрагменты документов.

Команды: `/start`, `/forget` — забыть историю, `/clear` — удалить документы, `/memory` — состояние обеих памятей.

## Как устроена память в ботах

### Короткая память (history buffer)

**Что это.** Скользящее окно из последних `MEMORY_SIZE` (по умолчанию 10) реплик диалога,
в котором модель «помнит», о чём вы говорили минуту назад.

**Как сохраняется.** Память живёт в оперативной памяти процесса — это обычный Python-`dict`:

```python
# bot_short_memory.py / bot_combined_memory.py
history: dict[int, list[dict[str, str]]] = {}
# { 123456789: [{"role": "user", "content": "Привет"},
#               {"role": "assistant", "content": "Привет! Чем помочь?"}, ...] }
```

Ключ — `user_id` из Telegram, поэтому диалоги разных пользователей не пересекаются.
Каждая новая реплика добавляется в конец списка, а список обрезается по хвосту:

```python
messages.append({"role": role, "content": content})
if len(messages) > MEMORY_SIZE:
    history[user_id] = messages[-MEMORY_SIZE:]
```

**Ограничения.** Такая память исчезает при перезапуске скрипта и занимает место в RAM.
Именно поэтому для знаний, которые должны переживать рестарт, используется долгая память.

**Библиотеки.** Отдельные не нужны — достаточно `dict` и `list` из стандартной библиотеки.

### Долгая память (RAG + векторная база)

**Что это.** Семантическая память по документам: текст хранится не дословно, а в виде
векторов, и находится по смыслу, а не по точному совпадению слов.

**Как сохраняется.** Используется **ChromaDB** в режиме persistent storage — база лежит
на диске в папке `./memory` и переживает перезапуск:

```python
chroma_client = chromadb.PersistentClient(path="./memory")
collection = chroma_client.get_or_create_collection(
    name="documents",
    metadata={"hnsw:space": "cosine"},   # поиск по косинусному расстоянию
)
```

Путь записи документа:

1. **Скачивание** файла из Telegram (`bot.download_file`) во временный `temp_<uuid>.<ext>`,
   который удаляется в `finally`.
2. **Извлечение текста** — `load_document()`: `PyPDF2` для PDF, `python-docx` для DOCX,
   обычное чтение для TXT.
3. **Разбиение на чанки** — `chunk_text()` нарезает текст по ~500 символов с перекрытием
   50 символов. Граница сдвигается назад к `.`/`!`/`?`, чтобы не рвать посреди мысли.
   Перекрытие нужно, чтобы факт на стыке двух чанков не потерялся.
4. **Эмбеддинги** — `embed_chunks()` отправляет чанки в `/v1/embeddings`
   (`openai/text-embedding-3-small`) и получает векторы размерности 1536.
5. **Запись в базу** — `collection.upsert()` сохраняет вектор, исходный текст чанка
   и метаданные:

```python
collection.upsert(
    ids=[f"{doc_id}_{i}" for i in range(len(chunks))],
    documents=chunks,                              # текст для отдачи модели
    embeddings=embeddings,                         # векторы для поиска
    metadatas=[{"source": file_name,
                "doc_id": doc_id,
                "user_id": str(user_id)}],         # изоляция пользователей
)
```

`user_id` в метаданных позволяет фильтровать выдачу, чтобы документы одного пользователя
не попадали в контекст другому.

### Логика запросов

**Эмбеддинги** (`/v1/embeddings`). Один или несколько текстов уходят в поле `input`,
в ответ приходят векторы в `data[i].embedding`. Ответ сортируется по `index`, чтобы
порядок векторов совпал с порядком чанков — иначе чанки «перемешаются» в базе.

**Поиск контекста** (`retrieve_context`). Вопрос пользователя сначала превращается
в вектор тем же эмбеддером, затем ChromaDB ищет ближайших соседей:

```python
results = collection.query(
    query_embeddings=await embed_chunks([question]),
    n_results=TOP_K,                 # 3 фрагмента
    where={"user_id": str(user_id)},  # только документы этого пользователя
)
```

**Генерация ответа** (`/v1/chat/completions`). Короткая и долгая память соединяются
в одном запросе к модели:

```
[system]    Правила + фрагменты документов (долгая память)
[user]      Реплика 1  ┐
[assistant] Ответ 2    │ короткая память — последние 10 сообщений
[user]      Реплика 3  ┘
[user]      Текущий вопрос
```

Фрагменты документов попадают в `system`-сообщение, поэтому они действуют как
инструкция на весь запрос, а история диалога остаётся отдельными сообщениями —
так модель корректно разрешает местоимения вроде «это» и «продолжи».

В `bot_short_memory.py` долгая память отсутствует: в `messages` идут только
`system`-инструкция и история. В `bot_long_memory.py` отсутствует короткая:
вопрос отправляется один, но с фрагментами.

Ответ модели берётся из `choices[0].message.content`. Все запросы к API идут через
`aiohttp` с таймаутом 120 секунд и ретраями (до 3 попыток с паузой 2 секунды),
а длинный ответ режется на части по 4096 символов — это лимит сообщения Telegram.

### Какие библиотеки за что отвечают

| Библиотека | Роль в памяти |
|------------|----------------|
| `aiogram` 3.x | Приём сообщений и файлов из Telegram, `user_id` как ключ памяти |
| `python-dotenv` | Загрузка `TG_BOT_API_KEY` и `PROXYAPI_API_KEY` из `.env` |
| `dict` / `list` (stdlib) | Короткая память: история диалога в оперативке |
| `chromadb` | Долгая память: векторный индекс с сохранением на диск в `./memory` |
| `PyPDF2`, `python-docx` | Извлечение текста из PDF и DOCX перед эмбеддингом |
| `aiohttp` | Асинхронные запросы к `/v1/embeddings` и `/v1/chat/completions` |
| `ProxyAPI` | Эмбеддинги `openai/text-embedding-3-small` и генерация `openai/gpt-5.6-luna` |

## Модели

| Задача | Модель |
|--------|--------|
| Генерация ответов (все боты) | `openai/gpt-5.6-luna` |
| Эмбеддинги (долгая память) | `openai/text-embedding-3-small` |

Идентификаторы моделей можно изменить в константах в начале каждого скрипта.
